## 2026-09-05 — Event household then two intro follow-ups (child-only + combo)

**Where:** Household Josh Coy (Active). Campaign “Sept Kids Wrestling Camp” → Event “Wrestling Tournament” / “Ninjas Bracket”. Guardian signed the child (Jaime, wrestling) up, staff processed to a Lead, Add person Self (Josh), Trial for adult, then Trial for child. Follow-up tab.

**What Scott saw**

1. Two open phone calls, both due Sep 8, 2026 5:00 PM, both Unassigned, both looking like intro confirmation:
    - Child only: Jaime Coy — Kids BJJ — Sep 7, 5:00 PM
    - Combo: Josh Coy — Adult BJJ — Sep 7, 6:00 AM **and** Jaime Coy — Kids BJJ — Sep 7, 5:00 PM
2. Add Self did not fill Josh from the household contact; staff had to type it.
3. Notes & History: `New → Trial scheduled · Trial scheduled.` (looks like a doubled transition).

**Cause — two follow-ups (not a broken INITIAL_SCHEDULE merge)**

This is not two intro-confirmation tasks racing. `ensureInitialFollowUpTask` still consolidates pending `INITIAL_SCHEDULE` onto one household call (public parent+child booking and “schedule dad then add child trial” tests still expect one).

The Event path creates a **different purpose**:

1. Process registrations → `ensureEventFollowUpTask` → one pending `EVENT_FOLLOW_UP` linked to Jaime’s LeadLine. Event attendance is not a Trial (household note is correct).
2. Staff schedules Josh’s Trial → `createTrial` → `ensureInitialFollowUpTask` only looks for pending **`INITIAL_SCHEDULE`**. It does not see the Event task, so it inserts a second pending `PHONE_CALL`.
3. Staff schedules Jaime’s Trial → that second task absorbs Jaime (`follow_up_task_lines`). Due date is not reset. Now INITIAL_SCHEDULE lists both intros.

The Follow-up cards never show `purpose`. Header is always `Phone call · Open`. “Confirm intros” is **not** “this task is INITIAL_SCHEDULE.” `confirmationIntros` is derived from any `SCHEDULED` Trial on linked lines. After Jaime’s Trial exists, the Event task (still linked to Jaime) renders the same Confirm-intros block as the intro call. Same due-at helper (two weekdays later 5:00 PM Denver) makes them look like duplicates of one job.

Architecture today: one pending `INITIAL_SCHEDULE` per household, **and** one `EVENT_FOLLOW_UP` per household+event. Overlapping acquisition calls to the same contact were not treated as one job.

**Cause — Add Self empty**

Event process creates the header from registration contact (Josh) and a `CHILD` line (Jaime). Guardian-only households have zero `SELF`. Add person defaults `newLine` to blank names + relationship `CHILD`. Choosing Self does not copy `lead.firstName` / `lastName` (or phone — phone stays on the header). Server `insertLeadLine` also does not default Self from the header. Prefill is a form convenience; identity is still a new LeadLine.

**Cause — history copy**

One header row: `NEW` → `TRIAL_SCHEDULED` with auto note `"Trial scheduled."` The UI prints status label and note, so it reads `New → Trial scheduled · Trial scheduled.` The second Trial does not write another header change (`TRIAL_SCHEDULED` is not in the auto-advance list). Not two transitions.

**Solution (implemented 2026-09-05)**

1. **One overlapping household call.** When a Trial is scheduled, if a pending `EVENT_FOLLOW_UP` already exists for that household, do not open a second pending phone call. Absorb intro lines onto one PENDING task (cancel or retarget the Event task with a note that intro confirmation superseded it, or attach Trials onto the Event task and stop creating `INITIAL_SCHEDULE` while that Event call is still open). Completed Event history stays. Regression: process Event (child only) → add Self → adult Trial → child Trial → **one** PENDING follow-up listing both intros.
2. **Show purpose on the card / queue** so Event follow-up cannot be mistaken for Confirm intros. Event tasks should show event title / attendance note, not later Trial datetimes, unless that task is the intro confirmation.
3. **Add Self prefill:** when the form relationship is Self (or when opening Add person on a household with no Self), copy header first/last name. Keep program/age empty. Do not invent a second contact phone on the line.
4. Optional copy: hide the status-history note when it repeats the to-status label.

Do not add `UNIQUE(leadId)` on pending `INITIAL_SCHEDULE`. Consolidation stays in `ensureInitialFollowUpTask`; the gap is Event vs intro purposes.

## 2026-09-04 — Campaign copy-link collapses the workspace header

**Where:** `/marketing/campaigns/:id` after New campaign → Copy default tracking link → Copy anyway (Draft).

**What Scott saw:** Confirm dialog in the top-left. After copy, “Test Camp” stacked one letter per line, overlapping Previous/Next, CAMPAIGN, and the Copy button. A long green “Copied http://localhost:5000/trial?c=…&utm_…” bar sat across the header.

**Cause (layout):** `copied` is the full tracking URL. That `AppAlert` lives in the header flex row next to `AppRecordSelector` (`sm:flex-row` identity `min-w-0 flex-1` vs actions `sm:w-auto`, no `min-w-0`). The URL has no spaces and `AppAlert` does not `break-all`, so the actions column’s min-content width is the whole URL. Flex `min-width: auto` will not shrink it. The identity column is the one allowed to shrink, so the title (`inline-flex` + `break-words`) wraps per character.

Event workspace already puts the copied alert **outside** that header row. Campaign Tracking tab already uses `break-all` for the same URL.

**Cause (dialog):** `AppConfirm` is a native `<dialog showModal>`. Tailwind v4 Preflight sets `margin: 0` on all elements, which removes the UA `margin: auto` that centers modals. Confirm therefore opens top-left. Not the letter-stack, but it is the first thing in this flow.

**Solution (do not implement until asked):**

1. Campaign header: short copy notice (“Copied the default tracking link.”), not the raw URL. Put it below the identity/actions row or in the workspace default slot like Events. If the URL stays on screen, `break-all` + `min-w-0 max-w-full` on the actions column.
2. `AppConfirm` `<dialog>`: restore centering (`m-auto`, or a base `dialog:modal { margin: auto }`).
3. Recheck Tracking-tab Copy link (same `copied` state) and Event Copy public URL so a long URL cannot crush those headers either.

## Response (troubleshooting only — do not implement until asked)

### 1. Consent copy — agree (copy only)

**Issue:** Public `/trial` says “It’s ok to text me about this intro.” Staff `/leads/new` says “SMS consent.” The gym also calls people. Checkboxes persist `smsConsent` / `emailConsent` only.

**Solution:** Change labels, not schema. Suggested:

- Public SMS box: “It’s ok to text or call me about this intro.”
- Public email box: keep “It’s ok to email me about this intro.”
- Staff SMS box: “OK to text or call”
- Staff email box: “OK to email”

Do not add a third consent column. Public `/events/:slug` has **no** consent boxes today — out of this item unless you want them added.

### 2. Roster attendance — agree (missing save feedback)

**Issue:** Attendance `<select>` PATCHes immediately (`setAttendance` → `/api/marketing/events/lines/:id`) then refreshes the Event. No per-row saving/saved/error. Failures go to a page-level alert that is easy to miss. Same pattern on Exclude-from-processing.

**Solution:** Per-row state on that control: disable while in flight, brief “Saved” (aria-live) on success, inline error on failure. Do not add a second Save button. Mirror on the exclude checkbox if it is in the same table.

### 3. Same-phone Event registrations

**3a. No warning on public signup or Roster — agree (UX gap)**

Public `/events/:slug` and staff add-registration do not look up existing Event registrations or CRM households. Duplicate phones are allowed on purpose (Event rows are not Leads yet). Staff `/leads/new` already warns. Public `/trial` does **not** warn the customer either (staff-only possible-duplicate).

**Solution:** Staff Roster: badge rows that share a normalized phone/email with another registration on this Event, and optionally with an existing household (same matcher as process). Public form: do **not** block signup; optional “we already have a registration for this phone” is a product choice — ask before adding customer-facing duplicate copy.

**3b. Process did not create a second Follow-up — not a bug**

Same normalized phone is one `contactKey` group. Batch creates **one household** and **one** `EVENT_FOLLOW_UP` per household+event (`ensureEventFollowUpTask`). A second registration links people onto that call; it does not add another `/tasks` row. Preview “Follow-up calls” is households in the batch, not registration count.

**Solution:** Show the grouped people on Process (see Process-tab note). Copy: “One confirmation call per household for this event.”

**3c. See who is already processed — agree**

Same as the Process-tab note. Roster “Open household” / “Not processed” is the only current tell.

### 4. Compensation credit — discussion, no code change

**Today:** SYSTEM credit is Campaign **owner** when the household has campaign/tracking/event evidence. Walk-in with no campaign stays UNASSIGNED. Follow-up assignee is never credit. Manual correction exists.

**Your rule:** any in-app tracking link credits **you**; walk-ins stay off campaign owners.

That conflicts with current SYSTEM behavior. Do not change credit rules until this is decided. Options to discuss: (A) always credit a gym default user (you) when evidence is an app tracking link; (B) keep campaign owner; (C) UNASSIGNED until you assign. Walk-ins with no link stay UNASSIGNED in all three.

### 5. Permissions — deferred

### 6. Household status after convert/lost + trial no-show — agree (bug + open product question)

**What happened:** Mixed JOINED+LOST correctly showed “Closed · mixed outcomes.” Header JOINED/LOST is demoted, so stored header is still an operational status (often Trial attended). Recording No-show on the lost person’s still-`SCHEDULED` Trial:

1. `setTrialOutcome` writes header `NO_SHOW` because header is not JOINED/LOST.
2. It also `changeLeadLineStatus` LOST → NO_SHOW. The auto note “Trial no-show.” satisfies the correction-note rule, so Lost is **reopened** without an explicit reopen.

Attended on the converted person did nothing because that Trial was already not `SCHEDULED` (outcome buttons only apply to a scheduled intro).

If JOINED remains, derived display should be “Active · mixed outcomes,” not “No-show.” A literal household badge “No-show” means the UI fell through to header status (no JOINED/LOST left in the lines passed to `householdDisplayStatus`) or the person card was read as the household. Either way, Trial outcome must not silently reopen a terminal person or rewrite household header.

**Solution (behavior):** Skip line/header status writes in `setTrialOutcome` when that person is JOINED or LOST. JOINED still needs reverse conversion; LOST still needs explicit reopen. Recording intro attendance is not reopen. Tests: JOINED+LOST stays Closed · mixed after a Trial outcome on either person.

**Mixed household label (your larger question):** I will not invent a new scheme. Current matrix: all Joined → Joined; all Lost → Lost; Joined+Lost and no open people → Closed · mixed; any Joined or Lost plus an open person → Active · mixed; else the latest operational header (Trial scheduled / Attended / No-show). That last fallback is why one No-show can dominate the badge. Decide later whether the household badge should stay coarse (mixed/active/closed) or show a compact people summary (“Joined 1 · Lost 1 · No-show 1”). Until then, fix the reopen leak so a final person cannot drag the household backward.

### Your Q2 — Content/Asset navigation and many-to-many — discussion + small UX gap

**Stuck without the rail:** Content detail (`/marketing/content/:id`) has “Back to content queue” and a Campaign **select**, but **no** Campaign name link in the header. Marketing Tasks and Assets already link the Campaign. Campaign workspace Content/Assets tabs already create in context.

**Solution (navigation, no schema):** Same header link as Tasks/Assets: Campaign name → `/marketing/campaigns/:id`. Optional: “Back to campaign” when `?campaignId=` or `item.campaignId` is set.

**Many-to-many:** ContentItem has **one** optional `campaignId` today — not many-to-many. Assets have a primary `campaignId` plus `asset_usages` (asset ↔ campaign and/or content), so a file can already be attached in more than one place. Do not add Content↔Campaign many-to-many until you decide a Content item is reusable copy vs one campaign’s caption. A good asset used everywhere is already the usages table; the missing piece is mostly “how do I get back” and seeing every usage on the Asset record.
